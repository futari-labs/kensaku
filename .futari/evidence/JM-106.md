### Premise test and root cause (no Exa cost)

Fixes 1 and 2 shared one premise: "Playwright's `response.body()` gives the stream's UTF-8 bytes". It was tested directly against the built app in fixture mode (`NODE_ENV=test`, `KENSAKU_EXA_MODE=fixture`, scenario `xm5-jp`, the frozen S9 Japan search):

- Server, on the wire (curl and Node fetch): status 200, `content-type: text/event-stream` with no charset, 4772 bytes, valid UTF-8, holds `ソニー`, no mojibake.
- The suite's own capture (`captureQuery` in `scripts/live/browser.ts`): 5147 bytes, no `ソニー`, holds `ã‚½ãƒ‹ãƒ¼`. Reproduced offline.
- CDP `Network.getResponseBody` for the same request: `base64Encoded: false`, `charset: ""`, the body text already mojibake. Base64 handling cannot help, because Chromium never returns base64 for this response.
- Inverting the WHATWG windows-1252 mapping on the captured text (each code point back to its byte, then UTF-8) gives exactly 4772 bytes, equal to the wire bytes except the per-run `retrievedAt` stamps.

The premise is false. The SDK (`createUIMessageStreamResponse`, ai 7.0.178) encodes the stream with `TextEncoderStream` (UTF-8) but declares `text/event-stream` with no charset. The page's fetch reader decodes UTF-8, so the DOM is right. Chromium's network layer stores the body for DevTools as text decoded with the default windows-1252, and Playwright's `body()` re-encodes that text as UTF-8. The first wrong decision in our code is the server response that does not declare the encoding it uses. The same mojibake reaches `images[].candidates[].sourceTitle` (copied from the captured products), which is why images failed the caption check.
