# Stripe Checkout research (2026-11-23)

Purpose: verified external facts for adding Stripe-hosted Checkout (sandbox/test mode only, USD/SGD/JPY, no conversion) to the local Node 22 + Hono app on `http://127.0.0.1:8787`, with webhooks through `stripe listen` and network-free CI.

## Method

- Read the npm registry metadata for `stripe` and the published tarball of `stripe@23.1.0` (README, CHANGELOG, `.d.ts` files, `esm/Webhooks.js`, `esm/apiVersion.js`).
- Read docs.stripe.com pages as Markdown (`<page>.md`) on 2026-11-23. The live API reference shows `Stripe-Version: 2026-11-18.endive`.
- Read the official GitHub READMEs and source of `stripe/stripe-mock` and `stripe/stripe-cli` (raw.githubusercontent.com).
- No Stripe API call, account, or API key was used.

Labels: **VERIFIED** = stated on a page or in a file I read. **INFERRED** = follows from verified facts but is not stated directly. **UNVERIFIED** = I could not find an official statement.

## Facts

### 1. SDK (`stripe` npm package)

- **S1.** The newest stable `stripe` release published at least 2 weeks before 2026-11-23 (cutoff 2026-11-09) is **23.1.0**, published 2026-10-29T19:58Z. The next stable release, 23.2.0 (2026-11-19), is too new under the 2-week rule. The npm `latest` tag is 23.2.0. Source: https://registry.npmjs.org/stripe. **VERIFIED**
- **S2.** `stripe@23.1.0` pins API version **`2026-10-28.endive`**. CHANGELOG: "This release changes the pinned API version to `2026-10-28.endive`". `esm/apiVersion.js` contains `ApiVersion = '2026-10-28.endive'`. Source: https://github.com/stripe/stripe-node/blob/master/CHANGELOG.md (23.1.0 entry) and the 23.1.0 tarball. **VERIFIED**
- **S3.** Node support: `engines.node` is `">=20"`. The README says "we currently support all LTS versions of Node.js 20+". 23.0.0 dropped Node 18. The SDK versioning page lists Node 22 as supported (EOL April 2027, support dropped September 2028). Sources: https://registry.npmjs.org/stripe/23.1.0, https://docs.stripe.com/sdks/versioning?lang=node. **VERIFIED**
- **S4.** ESM/TypeScript import: `import Stripe from 'stripe';` then `new Stripe('sk_test_...')`. The README says to use a default import, "not `* as Stripe`". The package `exports` map gives ESM types at `./esm/stripe.esm.node.d.ts`. Request and response types are namespaced, for example `Stripe.Checkout.SessionCreateParams`. Source: https://github.com/stripe/stripe-node#usage-with-typescript. **VERIFIED**
- **S5.** Pin the API version with `new Stripe(key, { apiVersion: '2026-10-28.endive' })`. In 23.1.0, `StripeConfig.apiVersion` has type `LatestApiVersion` (`typeof ApiVersion`), so TypeScript accepts only the pinned literal. If `apiVersion` is unset, the SDK uses the version that was current when it was released (stripe-node v12 and later). You can also set `apiVersion` per request through `RequestOptions`. Docs warn that overriding it "might cause inaccurate Typescript types". Sources: README config table; `cjs/lib.d.ts`; https://docs.stripe.com/sdks/versioning?lang=node. **VERIFIED**
- **S6.** By default the SDK retries once (`maxNetworkRetries: 1`) and adds idempotency keys "where appropriate". The default timeout is 80000 ms. `maxNetworkRetries: 0` turns retries off, but one retry still happens on ECONNRESET/EPIPE. Source: https://github.com/stripe/stripe-node#network-retries. **VERIFIED**
- **S7.** Breaking change in 23.0.0 (endive): "⚠️ Remove support for `payment_method_types` on `Checkout.SessionCreateParams`". In 23.1.0, `SessionCreateParams` has `allowed_payment_method_types` (a filter on the dynamically eligible set) and `excluded_payment_method_types`, and has no `payment_method_types`. The current create reference also omits `payment_method_types`. Sources: stripe-node CHANGELOG 23.0.0; https://docs.stripe.com/api/checkout/sessions/create. **VERIFIED**

### 2. Checkout Session create (`mode: payment`, hosted)

- **S8.** `ui_mode` defaults to `hosted_page`. Other values are `embedded_page`, `form`, and `elements`. The response `url` "Applies to Checkout Sessions with `ui_mode: hosted_page`... only present when the session is active". Sources: https://docs.stripe.com/api/checkout/sessions/create, https://docs.stripe.com/api/checkout/sessions/object. **VERIFIED**
- **S9.** `line_items` is required for `payment` mode, with a maximum of 100 line items. Each item needs one of `price` or `price_data`, plus `quantity`. Source: https://docs.stripe.com/api/checkout/sessions/create?query=line_items. **VERIFIED**
- **S10.** `line_items[].price_data` fields:
  - `currency` (required): lowercase ISO code, must be a supported currency.
  - `unit_amount`: "A non-negative integer in the smallest currency unit". Alternatively `unit_amount_decimal`, with at most 12 decimal places. You must set one of the two.
  - One of `product` or `product_data`.
  - `product_data.name` (required).
  - `product_data.description` (optional).
  - `product_data.images`: "A list of up to 8 URLs".
  - `product_data.metadata`.

  Source: https://docs.stripe.com/api/checkout/sessions/create?query=line_items. **VERIFIED**
- **S11.** Docs on `success_url`: "The URL to which Stripe should send customers when payment or setup is complete." It is not allowed for `embedded_page` or `elements`. To get the session ID, add the literal `{CHECKOUT_SESSION_ID}`, for example `...?session_id={CHECKOUT_SESSION_ID}`. The docs say: "This is a literal string... Don't substitute it". Sources: create reference; https://docs.stripe.com/payments/checkout/custom-success-page?payment-ui=stripe-hosted. **VERIFIED**
- **S12.** Docs on `cancel_url` (optional): "If set, Checkout displays a back button and customers will be directed to this URL if they decide to cancel payment". Source: create reference. **VERIFIED**
- **S13.** `client_reference_id` is a string for reconciling with internal systems. Maximum 200 characters. Source: create reference. **VERIFIED**
- **S14.** `metadata` allows up to 50 keys. Keys can be up to 40 characters and values up to 500 characters. Keys can't contain `[` or `]`. Don't store sensitive data in metadata. Source: https://docs.stripe.com/api/metadata. **VERIFIED**
- **S15.** `expires_at` is an epoch time in seconds. It "can be anywhere from 30 minutes to 24 hours after Checkout Session creation". The default is 24 hours. Sources: create reference; https://docs.stripe.com/payments/checkout/how-checkout-works?payment-ui=stripe-hosted. **VERIFIED**
- **S16.** Payment-method defaults: "By default, Stripe enables cards and other common payment methods... In Checkout, Stripe evaluates the currency and any restrictions, then dynamically presents the supported payment methods". To limit the session to cards, use `allowed_payment_method_types: ['card']` (see S7). Sources: https://docs.stripe.com/payments/accept-a-payment?payment-ui=checkout&ui=stripe-hosted; create reference. The first part is **VERIFIED**. That `['card']` gives a card-only page is **INFERRED** from the parameter description.
- **S17.** Idempotency: the SDK request option is `idempotencyKey?: string` (in `RequestOptions`), for example `stripe.checkout.sessions.create(params, { idempotencyKey })`. Keys are up to 255 characters, and V4 UUIDs are suggested. For API v1, "you can remove keys from the system automatically after they're at least 24 hours old"; a reused key after pruning starts a new request. Retrying with different parameters returns an error. Stripe saves the result, including 500s, only after the endpoint starts executing. All v1 `POST` requests accept keys. Sources: https://docs.stripe.com/api/idempotent_requests; `cjs/lib.d.ts` in 23.1.0. **VERIFIED**
- **S18.** One currency per session: the Session object has a single `currency` field. The manage-prices docs say that prices, coupons, and shipping rates in one Checkout Session "must all have the same default currency, or else Stripe returns an error when you create the Checkout Session". Sources: https://docs.stripe.com/api/checkout/sessions/object, https://docs.stripe.com/products-prices/manage-prices. The single field and the same-default-currency rule are **VERIFIED**. The exact error for mixed-currency `price_data` items is **INFERRED**.
- **S19.** Adaptive Pricing can convert the displayed currency to the customer's local currency. `adaptive_pricing.enabled` "Defaults to your dashboard setting". It can be enabled in a sandbox. To guarantee no conversion, pass `adaptive_pricing: { enabled: false }`. Sources: https://docs.stripe.com/api/checkout/sessions/create?query=adaptive_pricing, https://docs.stripe.com/payments/currencies/localize-prices/adaptive-pricing?payment-ui=stripe-hosted. The default is **VERIFIED**. That passing `false` guarantees no conversion is **INFERRED**.

### 3. Localhost redirect URLs

- **S20.** The official hosted-Checkout quickstart tells you to set `success_url` to "for example, `http://localhost:4242/success.html`". Source: https://docs.stripe.com/payments/accept-a-payment?payment-ui=checkout&ui=stripe-hosted. **VERIFIED** for `http://localhost` in a testing environment. The docs never state that `http://127.0.0.1:8787` is accepted or that live mode rejects plain-HTTP or localhost URLs: **UNVERIFIED**. A cheap fallback: use `http://localhost:8787/...` if the first sandbox call rejects 127.0.0.1.

### 4. Currencies

- **S21.** API amounts use the currency's minor unit: "`1000` to charge 10 USD", and "`10` to charge 10 JPY (or any other zero-decimal currency)". For zero-decimal currencies, "to charge 500 JPY, provide an `amount` value of `500`". USD and SGD are two-decimal (cents). Source: https://docs.stripe.com/currencies. JPY as zero-decimal is **VERIFIED** (the page uses it as the zero-decimal example). SGD as two-decimal is **VERIFIED** by default: "Currencies are two-decimal currencies unless otherwise specified", and SGD is not among the special cases.
- **S22.** Minimum charge amounts: **0.50 USD**, **0.50 SGD**, **50 JPY**. "The minimum amount you can charge depends on the payout bank account settlement currency". Charges that need conversion "must meet the equivalent minimum of the settlement currency". Source: https://docs.stripe.com/currencies#minimum-and-maximum-charge-amounts. **VERIFIED**
- **S23.** Card maximums are limited by digit count: "12 digits for most card payments, for a maximum of 999,999,999,999 in minor units". American Express allows 9 digits in most currencies. "Card networks can impose charge amount limits that are more restrictive". For JCB, Diners, and Discover cards on Japanese accounts, the maximum is 99,999,999 JPY. Non-card methods: 8 digits for most currencies. Source: https://docs.stripe.com/currencies. **VERIFIED**
- **S24.** Presentment versus settlement: "If the charge currency differs from your settlement currency... Stripe converts the charge to your settlement currency". The zero-decimal list "might not be available in your specific country. For the list of presentment currencies for your country, see Supported presentment currencies" (a per-country selector). Source: https://docs.stripe.com/currencies. **VERIFIED**. Whether a given sandbox account can present SGD and JPY for cards depends on the account country and is **UNVERIFIED**, because the per-country table is rendered client-side and I did not read it. Treat this as a check to run during the first sandbox call.

### 5. Expiring a session

- **S25.** `POST /v1/checkout/sessions/{id}/expire` (SDK: `stripe.checkout.sessions.expire(id)`). "A Checkout Session can be expired when it is in one of these statuses: `open`". After expiry, "a customer can't complete a Checkout Session and customers loading the Checkout Session see a message saying the Checkout Session is expired". The call returns the Session with `status: "expired"` and `url: null`. It "Returns an error if the Checkout Session has already expired or isn't in an expireable state". Source: https://docs.stripe.com/api/checkout/sessions/expire. **VERIFIED**
- **S26.** The `checkout.session.expired` event "Occurs when a Checkout Session is expired". Source: https://docs.stripe.com/api/events/types. **VERIFIED**. That a manual expire (as opposed to timeout) emits this event is **INFERRED** from the event's wording.
- **S27.** The PaymentIntent behind a Checkout Session can't be confirmed or cancelled directly: "To cancel, expire the Checkout Session instead." Source: https://docs.stripe.com/api/checkout/sessions/object (`payment_intent`). **VERIFIED**

### 6. Webhooks

- **S28.** Signature: `stripe.webhooks.constructEvent(payload, header, secret, tolerance?, cryptoProvider?, receivedAt?)`. Pass the raw request body exactly as received: "this will not work with a parsed (i.e., JSON) request body". Docs also say: "Any manipulation to the raw body of the request causes the verification to fail." In Hono, read `await c.req.text()` (or an ArrayBuffer) before any JSON parsing. Sources: stripe-node README "Webhook signing"; https://docs.stripe.com/webhooks. The API is **VERIFIED**. The Hono method is **INFERRED**.
- **S29.** Default tolerance is 300 seconds: `Webhook.DEFAULT_TOLERANCE: 300` in 23.1.0. Docs: "Our libraries have a default tolerance of 5 minutes". "Don't use a tolerance value of `0`", because it disables the recency check. In 23.0.0 and later, passing 0 really skips the check. Sources: `esm/Webhooks.js`; https://docs.stripe.com/webhooks#preventing-replay-attacks; CHANGELOG 23.0.0. **VERIFIED**
- **S30.** Testing helper: `stripe.webhooks.generateTestHeaderString({ payload, secret })` returns a valid `Stripe-Signature` value for `constructEvent`. There is also an async variant, `generateTestHeaderStringAsync`. Tests can use any secret, for example `whsec_test_secret`. Source: stripe-node README "Testing Webhook signing". **VERIFIED**. The option list also accepts `timestamp` and `signature`, per `prepareOptions` in `esm/Webhooks.js`: **INFERRED** from source, not documented in the README.
- **S31.** Ordering: "Stripe doesn't guarantee the delivery of events in the order that they're generated". Docs: "Don't use `created` to determine event order or whether you've already processed an event. Track event IDs". Source: https://docs.stripe.com/webhooks#event-ordering. **VERIFIED**
- **S32.** Duplicates: "Webhook endpoints might occasionally receive the same event more than once... logging the event IDs you've processed". "In some cases, two separate Event objects are generated" (dedupe by `data.object.id` plus `event.type`). The fulfillment guide says your fulfill function "might be called multiple times, possibly concurrently, for the same Checkout Session". Sources: https://docs.stripe.com/webhooks#handle-duplicate-events, https://docs.stripe.com/checkout/fulfillment?ui=full-page. **VERIFIED**
- **S33.** Retries: in live mode Stripe retries "for up to three days with an exponential backoff". Events in a sandbox are retried "three times over the course of a few hours". Each retry gets a new signature and timestamp. Source: https://docs.stripe.com/webhooks#automatic-retries. **VERIFIED**
- **S34.** Response: "must quickly return a successful status code (`2xx`) before any complex logic that could cause a timeout". Source: https://docs.stripe.com/webhooks#quickly-return-a-2xx-response. **VERIFIED**
- **S35.** On the Event, `livemode` (boolean): "If the object exists in live mode, the value is `true`. If the object exists in test mode, the value is `false`." The Checkout Session object also has `livemode`. Source: https://docs.stripe.com/api/events/object. **VERIFIED**
- **S36.** Event API version: webhook events use the account's default API version unless the endpoint sets one. `stripe listen` uses the account default unless you pass `--latest`. Sources: https://docs.stripe.com/sdks/versioning?lang=node, https://docs.stripe.com/cli/listen. **VERIFIED**. As a consequence, event payload shapes may differ from the SDK's pinned 2026-10-28.endive types unless the sandbox default matches (**INFERRED**).

### 7. Events for one-time card payments

- **S37.** `checkout.session.completed`: "Occurs when a Checkout Session has been successfully completed". `checkout.session.async_payment_succeeded` and `checkout.session.async_payment_failed` cover delayed payment methods. `checkout.session.expired` is listed in S26. Source: https://docs.stripe.com/api/events/types. **VERIFIED**
- **S38.** `payment_status` has three values. `paid`: "The payment funds are available in your account". `unpaid`: "not yet available". `no_payment_required`: setup mode or no payment due. Session `status` is `open`, `complete` ("Payment processing may still be in progress"), or `expired`. The fulfillment guide fulfills when `payment_status != 'unpaid'`, on either `checkout.session.completed` or `checkout.session.async_payment_succeeded`. Sources: https://docs.stripe.com/api/checkout/sessions/object; https://docs.stripe.com/checkout/fulfillment?ui=full-page. **VERIFIED**
- **S39.** When a hosted page has a webhook endpoint registered for `checkout.session.completed`, Checkout waits up to 10 seconds for it before redirecting. "If you're using the Stripe CLI for local testing, Checkout redirects to the `success_url` immediately." Source: https://docs.stripe.com/checkout/fulfillment?ui=full-page. **VERIFIED**
- **S40.** Declined cards: "Checkout provides feedback to the customer when a card declines and allows them to try again." Source: https://docs.stripe.com/declines/card. **VERIFIED**. That the session therefore stays `open` until it completes or expires is **INFERRED**.
- **S41.** PaymentIntent timing: since API 2022-08-01, "A PaymentIntent is no longer created during Checkout Session creation in payment mode. Instead, a PaymentIntent is created when the Session is confirmed." The create response example shows `payment_intent: null`. Sources: https://docs.stripe.com/changelog/2022-08-01/deferred-paymentintent-checkout-session; create reference. **VERIFIED**
- **S42.** Whether a decline inside hosted Checkout emits `payment_intent.payment_failed` (the event "Occurs when a PaymentIntent has failed the attempt to create a payment method or a payment") is not stated on any Checkout page: **UNVERIFIED**. The design should not depend on it. Rely only on `checkout.session.*` events.

### 9. Sandboxes, keys, permissions

- **S48.** "Sandbox keys start with `pk_test_` for publishable keys, `rk_test_` for restricted keys, and `sk_test_` for secret keys." Live keys start with `pk_live_`, `rk_live_`, and `sk_live_`. Source: https://docs.stripe.com/keys. **VERIFIED**
- **S49.** A sandbox provisioned anonymously with `stripe sandbox create` returns a secret key shown in the docs example as `rkcs_test_abc123`. These sandboxes expire after 7 days unless claimed. Source: https://docs.stripe.com/cli/sandbox. **VERIFIED**. A key guard that accepts only `sk_test_` or `rk_test_` would reject that example, so the guard should accept a `_test_` marker and reject `_live_` (**INFERRED**).
- **S50.** Stripe recommends general sandboxes for new integrations and separate sandboxes for local development and CI. The legacy test mode sandbox shares some settings with live mode. Sources: https://docs.stripe.com/sandboxes, https://docs.stripe.com/testing-use-cases. **VERIFIED**
- **S51.** Restricted-key permissions:

  | Request | Permission |
  | --- | --- |
  | `POST /v1/checkout/sessions` (create) | `checkout_session_write` |
  | `GET /v1/checkout/sessions/{id}` (retrieve) | `checkout_session_read` |
  | `POST /v1/checkout/sessions/{id}/expire` | `checkout_session_write` |
  | `GET /v1/checkout/sessions/{id}/line_items` | `checkout_session_read` |

  Write implies read. Source: https://docs.stripe.com/keys/permissions-reference; https://docs.stripe.com/keys/restricted-api-keys. **VERIFIED**. Whether inline `price_data`/`product_data` also needs Products or Prices write is **UNVERIFIED**. A failed request's error names the missing permission (per the restricted-keys page).
- **S52.** `stripe listen` prints a webhook signing secret (`whsec_...`) for use in your app. "The webhook signing secret provided will not change between restarts to the `listen` command." The webhook guide's code comments say "If you're testing with the CLI, run 'stripe listen' to find the secret key". Sources: https://docs.stripe.com/cli/listen, https://docs.stripe.com/webhooks. **VERIFIED**

### 10. Stripe CLI

- **S53.** macOS install: `brew install stripe` (Homebrew). Stripe now recommends its installation script because "Package manager installations don't support automatic updates". `npx @stripe/cli` also works. Sources: https://github.com/stripe/stripe-cli#installation, https://docs.stripe.com/cli/install. **VERIFIED**
- **S54.** `stripe login` is a browser-based pairing flow in which you choose accounts, sandboxes, and live access. In CLI versions after v1.50.0, an Administrator must first enable access under Settings → Team and security → MCP and CLI access. `stripe login --interactive` accepts an API key. `stripe switch` selects another sandbox. Source: https://docs.stripe.com/cli/login. **VERIFIED**
- **S55.** `stripe listen --forward-to <url>` now requires `--events <comma list>`, `--all-snapshot`, or `--all-thin`; "Otherwise, the command exits with an error". The `*` wildcard isn't supported in `--events`. Requests "run in a sandbox by default" (`--live` is opt-in). `-H/--headers` forwards custom headers. Example: `stripe listen --events checkout.session.completed,checkout.session.expired,checkout.session.async_payment_succeeded,checkout.session.async_payment_failed --forward-to http://127.0.0.1:8787/webhooks/stripe`. Source: https://docs.stripe.com/cli/listen. **VERIFIED** (the example command is assembled from the documented flags).
- **S56.** Host header: the CLI builds a Go `http.NewRequest(POST, <forward-to URL>)`, copies the original Stripe request headers (including `Stripe-Signature`), and sets `req.Host` only when you pass a custom `Host` with `-H`. So the default Host is the host:port of the `--forward-to` URL (for example `127.0.0.1:8787`). Source: https://github.com/stripe/stripe-cli/blob/master/pkg/proxy/endpoint.go. The code path is **VERIFIED**. The resulting Host value is **INFERRED** from Go `net/http` semantics.
- **S57.** `stripe trigger checkout.session.completed` is a supported trigger. "Events are triggered by issuing HTTP requests against the Stripe API... all necessary API objects will be created", so it creates sandbox objects and is not usable offline. Source: https://docs.stripe.com/cli/trigger. **VERIFIED**
- **S58.** `--api-key <key>` is a global flag that "overrides your local configuration" for one-off commands. The environment variable `STRIPE_API_KEY` "take[s] precedence over all other values". You can also use `stripe config --set test_mode_api_key sk_test_...`. Source: https://docs.stripe.com/cli (Using Stripe API keys; Global Flags). **VERIFIED**

### 11. Offline mocking for CI

- **S59.** `stripe-mock` is maintained (latest release v0.206.0, 2026-10-01; repo not archived, last push 2026-11-17). Its README says it "does not attempt to reproduce the behavior of the real Stripe API at all". It is stateless, its responses are hardcoded, and it returns success instead of test-card errors. "If you have more sophisticated testing needs, you shouldn't use stripe-mock... For regression test suites, you should define your own mocks". Source: https://github.com/stripe/stripe-mock. **VERIFIED**
- **S60.** For deterministic CI, put the Stripe client behind a small port and inject a fake that returns fixed Session objects. Sign webhook fixtures with `generateTestHeaderString` and a fixed test secret (S30). Signing is local HMAC and needs no network. Basis: S30 and S59. **INFERRED** (recommendation).
- **S61.** You can point the SDK at another server with the `host`, `port`, and `protocol` config options, for example to reach a local stripe-mock. The README "strongly discourage[s] `http`" for real Stripe servers. Source: stripe-node README config table. **VERIFIED**

### 12. Labeling demo purchases

- **S63.** In a sandbox, "card networks and payment providers don't process payments" and API calls return simulated objects. Source: https://docs.stripe.com/keys#sandbox-versus-live-mode. **VERIFIED**. This supports labeling these purchases "simulated, no money moves".

- **S64.** `stripe events resend <event id>` resends an event; per the CLI reference it "forwards it to any running stripe listen session". Source: https://docs.stripe.com/cli (events resend). **VERIFIED** by the independent reviewer on 2026-11-23, not by the original research pass.
- **S65.** `stripe listen --print-secret` prints the webhook signing secret for the listener without starting to forward. Source: https://docs.stripe.com/cli/listen. **VERIFIED** by the independent reviewer on 2026-11-23.
- **S66.** The Checkout Session create reference marks the top-level `currency` as required only in `setup` mode; in `payment` mode the currency comes from the line items. Kensaku therefore omits it. Source: create reference, as read by the independent reviewer. ## Consequences for the plan

1. Pin `stripe@23.1.0` and `apiVersion: '2026-10-28.endive'` (S1, S2, S5). Do not send `payment_method_types`; it no longer exists in this API version (S7). Use `allowed_payment_method_types: ['card']` if card-only is required.
2. Send `adaptive_pricing: { enabled: false }` to keep the presented currency equal to the requested one (S19). Each session uses one currency (S18).
3. Encode amounts per currency: JPY whole yen, USD/SGD cents. Enforce minimums 50 JPY / 0.50 SGD / 0.50 USD (S21, S22). Whether SGD and JPY presentment works on the actual sandbox account must be checked live (S24, S46).
4. Fulfill only from verified `checkout.session.completed` or `async_payment_succeeded` events with `payment_status === 'paid'`. Dedupe by event ID and keep fulfillment idempotent per session ID. Return 2xx fast (S31-S34, S38). Never depend on `payment_intent.payment_failed` (S42).
5. The key guard should accept only test keys and reject `_live_` keys and `livemode: true` events. The guard must account for the `rkcs_test_` CLI-sandbox prefix (S35, S48, S49).
6. CI uses an injected fake client plus `generateTestHeaderString`. Use neither stripe-mock nor `stripe trigger` (S57, S59, S60).
